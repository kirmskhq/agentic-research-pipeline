# Конвейер рыночных исследований с самопроверкой

Превращает одну строку текста — «локальный сервис выгула собак, Telegram WebApp» — в отчёт
по рынку из шести разделов, опирающийся на живой веб-поиск, и сам решает, годится ли
результат для отправки платящему клиенту.

Это обобщённая версия конвейера, который работает в продакшене как платный продукт:
клиент платит картой, отчёт генерируется без участия человека, и оператор видит только те
отчёты, которые конвейер сам пометил как сомнительные. В репозитории оставлена механика,
платёжная интеграция убрана.

## Что получается на выходе

Markdown-отчёт из шести фиксированных разделов:

1. Описание сферы и ключевая терминология
2. Топ существующих игроков (РФ + 2–3 глобальных)
3. Ценовая раскладка и модели монетизации
4. Портрет клиента и чем он пользуется сейчас
5. Незакрытые сегменты и пробелы рынка
6. Рекомендации по позиционированию

Разделы 2–5 пишутся по результатам живого поиска и ссылаются на источники markdown-сносками.
В конце отчёта — внутренний блок для оператора, а не для клиента: вердикт, неисправленные
замечания, нерабочие ссылки, сноски, которые модель взяла не из поиска, а из своих общих знаний.

## Схема конвейера

```
бриф ──> план ──> поисковая фраза ──> веб-поиск (3 запроса × 4 результата, разделы 2–5)
                                              │
                                              ▼
                                6 разделов пишутся параллельно
                                              │
             ┌────────────────────────────────▼────────────────────────────────┐
             │   цикл критика по разделам (до 3 кругов, выход по вердикту)      │
             │                                                                 │
             │   критик(раздел) ──> ok ──────────────> раздел выходит из цикла  │
             │        │                                                        │
             │        └─> замечания + СВОИ поисковые запросы                    │
             │                  │                                              │
             │                  ├─> запросы выполняются (в рамках бюджета)      │
             │                  └─> переписывается ТОЛЬКО этот раздел ──> заново │
             └─────────────────────────────────────────────────────────────────┘
                                              │
            корректура ──> аудит противоречий между разделами ──> проверка ссылок
                                              │
                                              ▼
                              ВЫПУСКАТЬ  ──или──  ПРИДЕРЖАТЬ (позвать человека)
```

## Три вещи, ради которых стоит смотреть код

**1. Цикл идёт по разделам и выходит по существу, а не по счётчику.**
Наивная версия критикует весь отчёт один раз и один раз переписывает его целиком — один
проход, без проверки, что правка что-то исправила. Здесь каждый раздел оценивается отдельно,
переписываются только провалившиеся, и раздел покидает цикл в тот момент, когда критик
отвечает `ok`. Параметр `RESEARCH_MAX_CRITIC_ROUNDS` — это предохранитель, а не условие
выхода. Разница практическая: «дешёвые» разделы перестают жечь токены сразу, а упрямый раздел
виден как факт, а не растворяется в усреднённом «отчёт один раз отредактирован».

**2. Критик сам решает воспользоваться инструментом и сам пишет аргументы.**
Если раздел провален из-за того, что утверждение не подкреплено источником, критик не просто
жалуется — он возвращает собственные поисковые запросы:

```json
{"verdict": "fix",
 "issues": ["«около 40% пользователей» — процент без источника"],
 "search_queries": ["сервис выгула собак доля рынка 2026", "выгул собак статистика россия"]}
```

Эти запросы уходят в DuckDuckGo, результаты дописываются в контекст именно этого раздела, и
раздел переписывается уже с новыми данными. Это единственное место, где инструмент выбирает
модель, а не скрипт; всё остальное в конвейере — жёстко заданная последовательность, и
честнее об этом сказать, чем продавать «полную автономность».

**3. Прогон заканчивается вердиктом, а не отправкой.**
Детерминированные проверки (разделы, так и не прошедшие критика; отсутствующие или слишком
короткие разделы; нерабочие ссылки в сносках; сноски с доменом, которого не было ни в одном
результате поиска; противоречия между разделами) объединяются с решением модели-редактора.
`HOLD` попадает во внутренний блок отчёта, печатается в stderr, при желании пишется в
`$RESEARCH_VERDICT_FILE` и возвращается как **код выхода 3**, чтобы вызывающая система
придержала выдачу и позвала человека. Способность конвейера отказаться выпускать собственный
результат — это и есть разница между демо и продуктом, перед которым можно ставить форму оплаты.

## Насколько это «агентно»

Частично, и честный ответ полезнее модного слова:

| Свойство | Здесь |
|---|---|
| Многошаговый план с ролями (автор / критик / правщик / редактор) | да |
| Опора на найденные источники и проверка, что сноски действительно из поиска | да |
| Самооценка, меняющая ход выполнения (цикл выходит по вердикту судьи) | да |
| Вызов инструмента по решению модели, с аргументами от модели | да, в одном месте (догуглить) |
| План, выбираемый моделью — порядок стадий, пропуск стадий | нет, последовательность фиксирована |
| Открытый набор инструментов на выбор | нет, инструмент один: веб-поиск |
| Память между прогонами | нет, каждый прогон с нуля |

Итого: связка «оценщик → оптимизатор» с одной реальной точкой выбора инструмента и гейтом
качества — не автономный агент, и ему не нужно им быть, чтобы приносить деньги.

## Как запустить

```bash
cp .env.example .env    # вписать LLM_API_KEY (любой OpenAI-совместимый эндпоинт)
docker build -t research-pipeline:latest .
./run.sh "локальный сервис выгула собак" > report.md; echo "exit=$?"   # 0 = выпускать, 3 = придержать
```

Без Docker: `pip install "openai==2.38.0" "ddgs==9.14.4"`, затем
`python pipeline.py "..." > report.md`.

По умолчанию используется Yandex AI Studio с DeepSeek V3.2 (так сделано в продакшене — ради
качества русского языка и хостинга внутри страны); для OpenAI, DeepSeek напрямую, OpenRouter
или локального vLLM достаточно задать `LLM_BASE_URL` и `LLM_MODEL`.

## Стандарт отчётности и пример заказа

В `reporting_standard/` лежит ручная методика, с которой сверяется автоматический конвейер:
`00_master_methodology.md` (источники, типизация утверждений, экономика, приёмка),
`build_report_pdf.py` (markdown → клиентский PDF), `prompt_for_new_report.md` и шаблоны CSV.
`reports/2026-10-01_gostevye-planshety-dlya-oteley/` — готовый заказ по этой методике:
исходный запрос, факт-лист, реестр источников, внутренний QA, клиентский текст, PDF и письмо.

```bash
pip install reportlab
python reporting_standard/build_report_pdf.py final_client.md final_client.pdf --author "..."
```

## Тесты

```bash
python tests/test_pipeline.py
```

Шесть сценариев прогоняются офлайн — без ключа, без сети, без обращения к модели — за счёт
подставных вердиктов критика:

```
PASS | all sections pass first round: verdict=SHIP searches=12
PASS | critic orders a re-search, then passes: verdict=SHIP searches=14
PASS | section never passes → hold: verdict=HOLD reasons=['разделы [2] не прошли критика за 3 круга']
PASS | garbage critic answer → treated as fix: verdict=SHIP
PASS | editor gate says hold: verdict=HOLD reasons=['редактор: цифры выглядят выдуманными']
PASS | search budget caps extra searches: verdict=SHIP searches=14
```

Главный для ревью — четвёртый случай: нераспарсенный ответ критика считается провалом раздела,
а не молчаливым пропуском. Fail-closed, а не fail-open.

## Деньги и время

Один отчёт — примерно 25–40 обращений к модели и 12–20 поисковых запросов. В продакшене
замеренное время от начала до конца — 17–35 минут на одном и том же брифе; разброс даёт
провайдер, а не цикл (цикл добавляет один вызов критика на раздел за круг). Если обещаете
клиенту срок — считайте по верхней границе, а не по средней.

## Известные ограничения

- Нет кеша между прогонами: одинаковые брифы оплачиваются дважды.
- Поиск работает только по сниппетам выдачи, страницы не скачиваются — факт, лежащий в теле
  статьи, для модели невидим.
- Критик и автор — одна и та же базовая модель, это ограничивает глубину разбора; вынести
  критика на другую (или более крупную) модель — очевидный следующий эксперимент.
- Порядок и число разделов фиксированы: бриф, которому нужна другая форма отчёта, её не получит.
- Все промпты на русском; перевод — механическая работа, здесь не сделана.
